# Haskell SDK Guide

You are helping a user work with panproto's Haskell bindings. The binding reaches the whole C ABI: schema, protocol, migration, morphism (hom) search including the span search, diff and compatibility classification, instance build and JSON I/O, lens and protolens algebra, the GAT layer (theories, free models, morphism checking), the expression language, version control, data versioning, and graph/fibre introspection, with parsing, multi-file project assembly, and git import behind cabal feature flags.

The C ABI is the ceiling. Haskell and Swift both reach it exactly and are at parity with each other; the Python SDK exceeds both, because `panproto-py` is a PyO3 extension linking `panproto-core` directly and so reaches 52 members with no `pp_*` entry point behind them (schema-document and IDL parsing for 106 protocols, version-control porcelain beyond the 13 operations the ABI carries, theory-DSL loading, hint-steered lens generation, runtime grammar override). That delta is architectural. "Parity with Python" means extending the ABI.

## Installation

The cabal package is `panproto` (version tracks the workspace, currently 0.71.0):

```cabal
build-depends: panproto >= 0.71 && < 0.72
```

The FFI backend links `libpanproto_c`, which is not redistributable through Hackage, so the package is source-first. Two bootstrap paths in `bindings/haskell/bootstrap/`:

- `dev-link.sh`: builds `panproto-c` and the C glue from source (cargo + a system C compiler), stages them under `bindings/haskell/.panproto-c/`, and writes `cabal.project.local`. Set `PANPROTO_C_FEATURES=full` (and pass the matching `-f parse -f project -f git` to cabal) for the gated cold-path surfaces.
- `fetch-bindist.sh`: downloads the prebuilt `libpanproto_c` from the matching GitHub Release.

Then `cabal build` / `cabal test`. The binding is gated on every panproto PR by the `Haskell SDK` CI job (builds the lib from source, runs the suite against the FFI backend and `native-only`).

## Architecture: two backends, one set of typeclasses

### Native backend

Pure-Haskell implementation of the runtime-free subset (protocol round-trip, the structured `Schema` ADT and its codecs, the pure lens/migration/expression value algebra, the algebraic-law instances). Use it for a Rust-runtime-free dependency, embedding in an existing Haskell pipeline, or property-testing the canonical exchange format. Engine-backed operations are `Rust`-only and produce a compile-time "no instance" error under `Native` (honest and discoverable).

### Rust backend

FFI-backed implementation linking `libpanproto_c` (the C ABI generated by `safer-ffi`), now over **122 frozen `pp_*` entry points** covering every domain (`CONTRACT.md` groups them: 4 lifecycle, 2 protocol, 7 schema, 5 check, 8 mig, 7 hom, 4 instance, 6 registry, 19 lens, 9 gat, 5 expr, 5 enriched, 13 vcs, 6 data, 5 graph, plus the feature-gated 10 parse, 6 project, 1 git). The `hom` group went from five exports to seven in 0.71.0, gaining `pp_hom_find_span` and `pp_hom_span_to_overlap`:

- **Hot path**: opaque `u32` handles into a **process-global** slab with no serialization per call. The slab is a `Mutex`-guarded global (not thread-local), so a handle stays valid across OS threads under GHC's threaded runtime; allocation, lookup, and free are all safe to interleave across threads.
- **Cold path**: CBOR via `ciborium` (Rust) / [`cborg`](https://hackage.haskell.org/package/cborg) (Haskell) for structured types, with a drained `ErrorEnvelope` carrying the failure detail.

## Capability typeclasses (one per domain)

Domain verbs live in a capability class per domain, each parameterised by a backend tag (`Native` or `Rust`), returning plain `IO`:

`ProtocolBackend`, `SchemaBackend`, `SchemaValidate`, `SchemaEngine`, `InstanceBackend`, `IoBackend`, `MigrationBackend`, `CheckBackend`, `HomBackend`, `LensBackend`, `GatBackend`, `ExprBackend`, `VcsBackend`, `DataBackend`, `GraphBackend`, plus the feature-gated `ParseBackend`, `ProjectBackend`, `GitBackend`.

Each follows the established shape: an associated `data ...Rep back`, an `ingest`/`reify`/`release` bridge, then the domain verbs. `Panproto.Class` holds the foundational `ProtocolBackend`/`SchemaBackend`/`SchemaValidate` + the `Native`/`Rust` tags; the rest live in their domain module (e.g. `MigrationBackend` in `Panproto.Migration`). The umbrella `import Panproto` re-exports everything.

### `HomBackend` changed shape in 0.71.0

`HomBackend` gained two methods and a superclass, and **this breaks any
out-of-tree instance**. Neither method carries a default, so an instance must
implement both, and the class now requires a `ProtocolBackend` instance it did
not before:

```haskell
class
    (SchemaBackend back, ProtocolBackend back, MigrationBackend back) =>
    HomBackend back
  where
    findMorphisms   :: SchemaRep back -> SchemaRep back -> SearchOptions -> IO [FoundMorphism]
    findBestMorphism:: SchemaRep back -> SchemaRep back -> SearchOptions -> IO (Maybe FoundMorphism)
    findSpan
        :: SchemaRep back -> SchemaRep back -> ProtocolRep back
        -> SearchOptions -> DomainConstraints -> IO FoundSpan
    spanToOverlap   :: Proxy back -> FoundSpan -> IO SchemaOverlap
    induceSchemaMorphism     :: TheoryMorphism -> SchemaRep back -> IO SchemaMorphism
    induceMigrationFromTheory
        :: TheoryMorphism -> SchemaRep back -> SchemaRep back
        -> IO (SchemaMorphism, CompiledRep back)
```

`findSpan` is the method to reach for when `findBestMorphism` answers
`Nothing`, which for schemas that were not built from each other is the
ordinary case. It never refuses for want of a match: two schemas with nothing
in common give an empty apex. The `ProtocolRep` is an argument because the apex
is a schema, a schema is well formed only against a protocol, and a schema
stores only its protocol's name.

`FoundSpan` carries `apex`, `left`, `right`, `quality`, `qualityLo`,
`qualityHi`, `apexCoverage`, `provenOptimal`, `isTotal`, `apexDigest` and
`legsAreFunctorial`. The last two are new in 0.71.0 and are what let a host
dedupe or cache a span it has just been handed: there is no schema-digest entry
point on the ABI and the CBOR a host holds is not the digest's pre-image, so
without `apexDigest` the identity was unreachable rather than merely
inconvenient. Both decode with `serde(default)`, so a host encoding the older
nine-key form for `spanToOverlap` is still decoded rather than answered with a
serialization error.

`SearchOptions` renamed `initial` to `hardPins`, to say what it does: a hard
restriction the search may not reconsider, not a starting point. `preferred`,
`maxNodes`, `relaxEdgeNamePruning` and `nameSimilarityThreshold` are gone.

`DomainConstraints` and `CostWeights` are new payloads a Haskell host can send,
with their defaults and codecs: `restrictedDomains`, `excludedTargets`,
`excludedSources`, and `scoringWeights`, the last carrying five components
(`name`, `edge`, `prop`, `degree`, `anchor`) checked and normalised by their
sum. None of this crossed the C boundary before.

`findMorphisms` returns the morphisms *attaining* the optimum rather than the
whole hom-set, so every element carries the same quality and there is no worse
tier further down the list. An empty list means no total morphism exists, and a
search that could not be posed or could not finish throws rather than returning
empty.

## Structural types that changed

`RecursionPoint` lost `muId` and now carries only `targetVertex`. The marker
vertex is the key the point is filed under in the schema's `recursionPoints`
map, and naming it twice made the two copies independently settable, which
deserialisation could not rule out. `SchemaDiff`'s `addedRecursionPoints` and
`removedRecursionPoints` carry `(Text, RecursionPoint)` pairs instead, so a
report still names the marker.

## Standard-class integration

Where a panproto structure already is a known algebra, the binding gives it the corresponding standard class:

- **`Semigroup` / `Monoid` / `Control.Category.Category`.** `Migration` is a `Semigroup` under structural composition (`(<>)` reads left-to-right as a data-flow pipeline). It is deliberately **not** a `Monoid`: composition is drop-on-miss (a vertex the right migration does not map is removed, mirroring `panproto_mig::compose`), so it has no schema-independent unit; the real identity is the per-schema self-map `identityMigrationOn :: [Text] -> [Edge] -> Migration` (and `emptyMigration` is the builder's zero, an annihilator under composition, not a unit). `ProtolensChain` **is** a `Monoid` (step concatenation; the empty chain is a genuine unit) with `LensArr` its `Category` wrapper, and `OpticKind` is a `Monoid` under the optics lattice (`Iso` the unit, `Traversal` absorbing).
- **Exception hierarchy.** `SomePanprotoError` is the umbrella; each surface has a child (`SchemaValidationError`, `CheckError`, `ExistenceCheckError`, `ExprError`, `GatError`, `GitBridgeError`, `IoError`, `LensError`, `MigrationError`, `ParseError`, `ProjectError`, `VcsError`, plus the fallback `PanprotoError`). A thrown child is catchable both at its own type and as `SomePanprotoError`; distinct children never alias.
- **`Hashable` / `Eq` / `Ord`** mirror the Rust derives, so the value types key `unordered-containers` maps as the Rust side does.

## Builders

`State`-monad builder DSLs with `do`-notation, mirroring the Python builders:

```haskell
sch = buildSchema "atproto" $ do
  vertex Vertex {id = "post", kind = "record", nsid = Just "app.bsky.feed.post"}
  vertex Vertex {id = "text", kind = "string", nsid = Nothing}
  edge Edge {src = "post", tgt = "text", kind = "prop", name = Just "text"}

mig = buildMigration $ do
  mapVertex "post" "note"
  resolve "post" "text" Edge {src = "note", tgt = "text", kind = "prop", name = Just "text"}
```

`SchemaBuilderM`, `TheoryBuilderM`, `MigrationBuilderM` (and `ProjectBuilderM`) are `State`-newtype monads; `build*` materializes the value.

## Effect layer

A first-class effect layer, baked into the package (no separate adapter):

- `class MonadIO m => MonadPanproto m where liftPanproto :: IO a -> m a`, with instances for `IO`, `ReaderT`, `StateT` (lazy and strict), and `ExceptT`.
- Under the `effectful` cabal flag, an `effectful` `Panproto` effect plus `runPanproto`, and a `MonadPanproto (Eff es)` instance.

Backend dispatch (`Native` vs `Rust`) and carrier dispatch (`IO` vs `Eff`) stay orthogonal: the capability classes return `IO`, and the effect layer lifts them.

## Lenses

panproto lenses are Cambria-style **asymmetric delta lenses with a complement** (`get : s -> (a, c)`, `put : (a, c) -> s`), verified at runtime through the engine, not van Laarhoven optics. The core type is self-contained: `lensGet`, `lensPut`, `checkGetPut` / `checkPutGet` / `checkLaws`.

Under the `optics-adaptors` / `lens-adaptors` cabal flags, `Panproto.Lens.Optics` exposes the structurally-lawful projections as genuine [`optics`](https://hackage.haskell.org/package/optics-core) / [`lens`](https://hackage.haskell.org/package/lens) optics: read-only `Getter`s over the structural values, and lawful `Lens'`es over plain record fields. A complement-carrying delta lens cannot be a lawful `Lens'` (forcing it would drop the complement and break `GetPut`), so only the lossless subset is exposed that way; the Haddock documents precisely which laws hold.

## Panic safety

Every status-returning `#[ffi_export]` is wrapped in a `guard(...)` that catches unwinds and returns an `i32` `PpStatus`; the buffer-free entry uses `catch_unwind` directly. Failures carry a CBOR `ErrorEnvelope` drained via `pp_last_error_take()`, mapped to the exception hierarchy above. The release profile uses `panic = "unwind"` (not abort), so a panic never tears down the GHC runtime. Input and output buffer marshalling is exception-safe end to end.

## cabal flags

| Flag | Default | Effect |
|------|---------|--------|
| `rust` | on | FFI backend (links `libpanproto_c`) |
| `native-only` | off | pure-Haskell only, no FFI dependency |
| `parse` | off | tree-sitter parse surface (`full-parse`-gated C entry points) |
| `project` | off | multi-file project assembly |
| `git` | off | git-import surface |
| `optics-adaptors` | off | `optics-core` adaptors for the lens surface |
| `lens-adaptors` | off | `lens` (van Laarhoven) adaptors |
| `effectful` | off | `effectful` effect for panproto operations |

The bootstrap scripts must build `panproto-c` with the matching cargo features so the linked symbols exist (`PANPROTO_C_FEATURES`).
